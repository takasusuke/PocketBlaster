# PocketBlaster 要件定義

`PocketBlaster`は作業名（未決 → 本ファイル末尾の未決事項）。

## 1. 決定済み事項

| 項目 | 内容 |
|---|---|
| ジャンル | アーケードガンシューティング（FPS視点）。当初はオンレール式だったが、
  自由に歩き回れる方式へ変更（2026-09-06、§8参照） |
| プレイ人数 | シングルプレイヤー |
| プラットフォーム（ゲーム本体） | PC（Unity） |
| 入力デバイス | スマホ（ブラウザ）を銃に見立てて狙う |
| 通信方式 | 同一Wi-Fi内、スマホのブラウザ → PCゲーム本体へWebSocketでジャイロ値を送信 |
| スマホ側アプリ形態 | ネイティブアプリ化しない。ブラウザで完結させ、ストア審査を不要にする |
| 狙いの決め方 | スティック/カーソルでの選択ではなく、スマホの物理的な向き（ジャイロ）で狙点を動かす |
| スマホの持ち方 | 縦持ちではなく「銃のように構える」持ち方。カメラはテレビ・PC画面を向かない |
| トラッキング方式 | ジャイロ（相対回転）＋リロード動作に紐づけた手動リキャリブレーション（簡易版） |
| モチーフ・世界観のトーン | 怖くないもの（ホラー系は除外） |
| 世界観・敵モチーフ | 野菜×ゾンビ。サバイバル環境で、襲ってくる野菜ゾンビを倒して「ジュース」にする
  （2026-09-06決定）。ホラーのパロディだが野菜×コミカルな見た目のため「怖くない」を満たす |

## 2. 体験の核

「画面に映る敵を、実際に銃を構えるように狙って撃つ」感触そのものが体験の核。
ボタン選択・スティックでのカーソル移動に逃げた瞬間、この企画の存在意義が消える。
既存のライトガン専用ハード（Wiiザッパー、Time Crisisの専用筐体等）を持たない前提で、
「手元にあるスマホ」だけでその感触にどこまで近づけるかが挑戦の核心。

## 競合調査

- **House of the Dead / Time Crisis / Point Blank（アーケード）**: 専用ライトガン筐体＋
  CRT/センサーバーによる絶対位置トラッキングが前提。画面のどこを狙っているかを筐体側が
  常に正確に把握できる構造で、本企画とは前提が異なる（後述）。
- **Sinden Lightgun（現行の家庭用ライトガン再現ペリフェラル）**: Webカメラで画面の縁
  （白枠）を認識し、実銃型デバイスの向きから画面上の狙点を絶対座標で逆算する方式。
  現行で最も精度が高いDIY/市販ソリューションだが、**「デバイスのカメラが常に画面を
  向いている」ことが前提**——本企画の「スマホを銃のように構える」持ち方（カメラが
  画面を向かない）とは根本的に相容れない。
- **Wii リモコンのIRセンサーバー方式**: センサーバー（赤外線の基準点）を画面上/近傍に
  固定し、リモコン側のIRカメラでそれを捉えて絶対位置を算出する方式。原理はSindenと同じ
  「外部の絶対基準点＋カメラ」で、同じ理由で本企画の持ち方とは両立しない。
- **スマホの姿勢センサーのみで狙いを取るアプリ・ミニゲーム**: `DeviceOrientationEvent`
  （iOS/Android双方のモバイルブラウザで対応、iOSは`requestPermission()`による明示許可が
  必要）は相対的な姿勢変化しか取れず、外部の絶対基準を持たないため、使い続けると
  ジャイロドリフトで狙点が実際の向きからずれていく。ARベースの照準ゲーム等はカメラ映像
  そのものを狙いの基準にすることでこの問題を避けているが、これも「カメラが画面を向く」
  前提であり本企画には使えない。

**差別化・結論**: 本企画が置かれた制約（カメラが画面を向かない持ち方）の下では、
外部の絶対基準点を使う既存方式（Sinden、Wiiリモコン方式）はいずれも採用できない。
残る現実的な選択は「ジャイロによる相対追従＋定期的な手動リキャリブレーション」であり、
これは妥協ではなく**この持ち方を選んだ時点で唯一整合する方式**。リキャリブレーションを
「リロード」という本来のガンシューティングの操作に重ねることで、UI的な違和感ではなく
ゲームプレイの一部として狙い直しを組み込む。この「制約から逆算した設計」自体が、
既存のライトガン専用ハード前提のタイトルにはない差別化点になる。

## 3. なぜこの方式か（技術的根拠）

- ジャイロ/加速度センサーは相対値しか取れないため、使用時間が延びるほど実際の向きと
  画面上の狙点がずれていく（ドリフト）。
- 本企画はスマホのカメラが画面を向かない持ち方を選んでいるため、カメラによる絶対位置
  補正（Sinden方式・ARマーカー方式）は使えない。
- 消去法として残る現実解は「相対追従＋手動リキャリブレーション」。リロード（弾切れ時に
  画面中央へスマホを構え直す動作）にリキャリブレーションを紐づけることで、プレイヤーに
  「システムの都合による操作」ではなく「ゲーム内の自然な動作」として提示する。
- iOS Safariでは`DeviceOrientationEvent.requestPermission()`によるユーザー操作起点の
  明示許可が必須（**要検証** — 実機での動作未確認、→ 未決事項）。

## 4. マイルストーン

| # | マイルストーン | 目的 |
|---|---|---|
| 1 | スマホブラウザ→PC間でジャイロ値をWebSocketで飛ばし、PC側で3D空間内のカーソル/照準を
    動かせることを確認する | 「狙って動かす」感触が本当に成立するかを最速で検証する |
| 2 | リロード動作でのリキャリブレーションを実装し、ドリフトが実用上気にならない範囲に
    収まるか検証する | この企画の技術的な核心である不変条件2（`CLAUDE.md`）の成立可否を
    確定させる |
| 3 | 固定敵1体を撃つだけの最小シーンを作り、「撃つ」感触（着弾フィードバック・効果音・
    敵の反応）を詰める | 体験の核（§2）を実際に触って判断する |
| 4 | オンレールの敵配置・複数ウェーブを持つ短い1ステージを作る | ゲームとしての手触りを
    通しで確認する |
| 5 | 世界観・敵モチーフを確定し、正式なアセットに差し替える | 見た目を「仮」から本番へ |

## 5. 検討事項

- WebSocketの遅延がプレイフィールにどこまで影響するか（同一Wi-Fi内なら数十ms程度を
  想定しているが実測が必要）。
- 難易度調整の手段（敵の出現速度・体力・弾数制限等）。
- スマホ側の画面表示（狙点そのものを表示するか、リロードのタイミングだけ表示するか等）。

## 6. 対象外

- マルチプレイヤー（協力・対戦とも）。
- Switch等の専用ハードへの展開（当初の企画動機である配信ハードルの高さを理由に除外）。
- スマホ側のネイティブアプリ化・ストア審査を要する構成。
- カメラを画面に向ける持ち方を前提にしたトラッキング方式（Sinden方式・ARマーカー方式等）。

**解決済み**:
- iOS Safariでの`DeviceOrientationEvent.requestPermission()`は実機で動作確認済み
  （2026-09-05、許可ダイアログが正しく表示されタップで許可できた）。
- 「ジュース」を得点要素にするかは、**得点要素にする**方向で解決（2026-09-06）。
  敵を倒すごとに得点が入り、ジュースの色付き飛沫（着弾演出）と合わせて「倒す＝ジュースを
  得点として稼ぐ」という一連の体験になっている。
- ジャイロ操作感・ドリフト・撃つ感触の実機での判断（2026-09-06、オーナー確認）:
  **「撃っていて楽しい。狙う感覚がいい感じ」**と肯定的な評価。この核心部分が
  成立していることが確認できたため、次の掘り下げとして反動・ヘッドショット等の
  部位別ダメージを実装した（§8参照）。

## 8. 将来の拡張

- **スコアリング（実装済み、2026-09-06）**: 敵を倒すごとに得点（`Target.PointValue`）が入り、
  ステージクリア時にシーン単位のローカルハイスコア（PlayerPrefs）と比較・更新する。
  タイムアタックや複数プレイヤー間のランキングは未決事項#5として残っている。
- **複数ステージ・ボス戦（実装済み、2026-09-06）**: `Milestone4_Stage`に加えて
  `Stage2_BossRush`（4ウェーブ、3発当てるまで倒れないパンプキンボス）を追加。
  `TargetHitState`の`hitPoints`で「倒れるまでの被弾数」を敵ごとに設定できる
  （通常の野菜ゾンビは1発、ボスは3発）。ステージ間の自動遷移は未決事項#6として残っている。
- **難易度モード（実装済み、2026-09-06）**: アーケード（HPゲージ制）／カジュアル（無制限）を
  選択できる。当初はスマホ側（接続前のラジオボタン）で選んでいたが、起動画面の新設
  （下記）に伴いPC側の起動画面へ一本化した。フェールの条件は当初「狙って撃ってはずした」
  ことだったが、実際に遊んでみて厳しすぎるという判断からオーナーが却下した
  （2026-09-06:「難易度モード「はずれ＝残機減少」は却下です」）。現在のフェール条件は
  「敵に近づかれ過ぎた」（`StageDirector.OnEnemyReachedPlayer`）と「高すぎる場所からの
  落下」（下記）のみ。`GyroReticleController.OnShotResolved`イベント自体は残っているが
  `GameSession`はもう購読しない。
- **体力ゲージ・被ダメージ源の拡張（実装済み、2026-09-06）**: 「残機」(`LivesState`、
  1回の被弾で全損)から「HPゲージ」(`PlayerHealthState`、最大100・整数の増減)へ移行した
  （オーナー要望:「プレイヤーの体力ゲージもUIとして実装してください」）。画面下に体力バー
  （track+fill、`GyroReticleController`のリロードバーと同じ構成）を表示する——当初は
  アーケードモードのみだったが、オーナー要望「体力バーはモードに限らず表示して」を受けて
  モードに関わらず常時表示に変更した。カジュアルモードでもダメージ・回復は同じように
  HPへ反映されるが、「無制限」の名の通りHPが尽きてもゲームオーバーにはしない
  （フェール判定はアーケードモードのみ）。敵接触は30ダメージ、体力回復アイテムは30回復
  （値は仮、実機での調整余地あり）。**未検証**: ダメージ量のバランス。
- **落下ダメージ（実装済み、2026-09-06）**: オーナー要望「あまりに高いところから
  飛び降りる場合にはダメージが入るようにしてください」を受けて追加。`Obstacle`に
  `IsPlatform`フラグ（`stepUpHeight`を無視して常に登れる足場）を新設し、
  `PlayerLocomotion`が直前の高さからの落差を追跡、安全な高さ(1.5m)を超えた分だけ
  `FallDamageCalculator`でダメージ量を算出して`GameSession`のHPへ反映する。
  各ステージに試作の足場(`Obstacle_Platform`、高さ3m)を1つ配置済み。
  **未検証**: 安全な高さ・ダメージ量の実機での調整。
- **反動・ヘッドショット等の部位別ダメージ（実装済み、2026-09-06）**: オーナー要望
  「まずは反動と、その反動コントロール要素として、敵のヘッドショットなど部位別の
  ダメージ量変化を実装してもらって試したい」を受けて追加。`GyroReticleController`が
  発砲のたびにレティクルを上へ弾き(`recoilKickPixels`)、時間経過で戻す
  (`recoilRecoverySpeedPixelsPerSecond`) — 連射するほど反動を自分で抑える必要が
  生まれる設計。各敵に`HeadHitbox`(子コライダー、`EnemyFactory`が生成)を追加し、
  頭部への命中を`Physics.RaycastAll`+距離ソートで優先判定、残り被弾可能回数を
  無視して即座に倒す(`TargetHitState.TryHit(isCritical: true)`)。ヘッドショットでの
  撃破は得点2倍(`StageDirector.HandleEnemyDefeated`)。**未検証**: 反動の強さ・
  ヘッドショット判定域の大きさ・位置の実機での調整。
- **アイテム(Pickup)の専用アート（実装済み、2026-09-06）**: オーナー要望「弾薬回復や
  体力回復の間にも画像を適用して」を受けて、体力回復(Health)・弾薬回復(Reload)の2種類に
  専用アート(`Assets/Resources/Pickups/`、ローカル画像生成)を追加した。`PickupFactory`は
  ランタイムコード(UnityEditor非依存)のため`Resources.Load`で読み込む——EnemyFactoryの
  Editorシーン構築時とは異なる仕組みが必要で、import設定(Sprite化)は新設の
  `PickupArtImporter`(Editor、`-executeMethod`で一度だけ実行)が担う。専用アートが
  無い種類(AmmoUp、最大弾薬数増加)は引き続き手続き生成の色分け円にフォールバックする。
- **起動画面（実装済み、2026-09-06）**: `Title`シーン（`TitleScreenController`）を新設。
  PC上のマウス操作だけで、難易度・SE音量・感度（`degreesToScreenPixels`相当）を選び、
  ステージ（`Milestone4_Stage`/`Stage2_BossRush`）のどちらかを選んでスタートできる。
  選択内容は`GameSettings`（PlayerPrefs）に保存され、次回起動時も覚えている。
  スマホ(`PhoneControllerServer`)には依存しないので、スマホをまだつながなくても
  起動画面の操作は完結する。これにより未決事項#6の一部（ステージの選び方）は解決した。
  ステージ終了後に起動画面へ戻る自動遷移(下記)を追加したことで、
  「毎回ここへ戻ってくる」画面としての役割がより強くなった。
- **プレイヤーの自由な歩き回り・フィールド障害物・パルクール（実装済み、2026-09-06）**:
  オーナー要望「プレイヤーがマップ内を動き回って、敵がプレイヤーの位置に近づいてくる
  ような遊び方にしてください」を受けて範囲を広げつつあったが、最終的に
  オーナー指示「自由に歩き回るようにします」で「オンレール式」（§1決定済み事項）を
  完全に撤回した。`StageDirector`はもうウェーブ間でプレイヤーの位置・向きを動かさない
  （カメラの自動Lerp移動を廃止）。`PlayerLocomotion.maxOffsetRadius`は9m→30mへ、
  さらにオーナー要望「移動できる範囲は6倍にしてください」で30m→180mへ拡大した
  （GroundFactoryで敷いた床の範囲に収まる緩い安全策という位置づけ）。
  移動速度(`stepDistance`)も「移動速度は3倍にしてください」で0.7m→2.1mに引き上げた。
  - **入力の切り替え**: スマホの傾きは1系統しか無く、狙い(既存の核となる操作)と
    移動が競合するため、「構える」ボタン（押している間だけ照準・離すと視界回転）で
    明示的に切り替える設計にした（オーナー指示）。構えていない間の視界回転感度
    (`LookSensitivity`)は「構えていない状態の感度を5倍にしてください」を受けて、
    既定・上下限とも範囲ごと5倍(既定60→300、上下限20-120→100-600)にした。
  - **構えていない間の発砲**: 以前は「構える」を押している間しか撃てなかったが、
    オーナー要望「構えていない状態でも撃つボタンを押したら、中央に撃つように
    してください」を受けて解禁した。構えていない間はレティクルが常に画面中央
    固定のため、追加の分岐無しでそのまま中央へ飛ぶ(`GyroReticleController.HandleShoot`)。
  - **障害物・パルクール**: `Obstacle`（低い箱は自動で乗り越え＝パルクール、高い壁は
    通れない、`IsPlatform`の足場は常に登れる）に加えて、オーナー要望「他にも
    オブジェクトを配置してください」「パルクールなども実装してください」を受けて
    `FieldObstacleScatterer`(新規Editor)を追加した。固定シードで低い箱・壁・足場を
    フィールド外周(半径40〜170m)へ40個ばら撒く`Scatter`と、高さ1→2→3→4mの足場を
    直線状に隣接させ実際に登れる`BuildParkourStaircase`の2種類を各ステージに配置した。
  - **未決着**: 敵(`EnemyApproach`)は障害物を避けずに直進するため貫通しうる
    （パスファインディング等は未実装）。フィールドの形状・障害物の量や配置は
    まだ試作段階で、実際に遊んでからの調整を前提にしている。**未検証**:
    移動速度3倍・移動範囲180mの体感、視界回転感度5倍の体感、追加オブジェクトの
    配置密度・パルクール構造物の登りやすさ。
