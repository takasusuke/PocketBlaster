# PocketBlaster 要件定義

`PocketBlaster`は作業名（未決 → 本ファイル末尾の未決事項）。

## 1. 決定済み事項

| 項目 | 内容 |
|---|---|
| ジャンル | オンレール式のアーケードガンシューティング（FPS視点） |
| プレイ人数 | シングルプレイヤー |
| プラットフォーム（ゲーム本体） | PC（Unity） |
| 入力デバイス | スマホ（ブラウザ）を銃に見立てて狙う |
| 通信方式 | 同一Wi-Fi内、スマホのブラウザ → PCゲーム本体へWebSocketでジャイロ値を送信 |
| スマホ側アプリ形態 | ネイティブアプリ化しない。ブラウザで完結させ、ストア審査を不要にする |
| 狙いの決め方 | スティック/カーソルでの選択ではなく、スマホの物理的な向き（ジャイロ）で狙点を動かす |
| スマホの持ち方 | 縦持ちではなく「銃のように構える」持ち方。カメラはテレビ・PC画面を向かない |
| トラッキング方式 | ジャイロ（相対回転）＋リロード動作に紐づけた手動リキャリブレーション（簡易版） |
| モチーフ・世界観のトーン | 怖くないもの（ホラー系は除外） |
| 世界観・敵モチーフ | 野菜×ゾンビ。サバイバル環境で、襲ってくる野菜ゾンビを倒して「ジュース」にする
  （2026-09-06決定）。ホラーのパロディだが野菜×コミカルな見た目のため「怖くない」を満たす |

## 2. 体験の核

「画面に映る敵を、実際に銃を構えるように狙って撃つ」感触そのものが体験の核。
ボタン選択・スティックでのカーソル移動に逃げた瞬間、この企画の存在意義が消える。
既存のライトガン専用ハード（Wiiザッパー、Time Crisisの専用筐体等）を持たない前提で、
「手元にあるスマホ」だけでその感触にどこまで近づけるかが挑戦の核心。

## 競合調査

- **House of the Dead / Time Crisis / Point Blank（アーケード）**: 専用ライトガン筐体＋
  CRT/センサーバーによる絶対位置トラッキングが前提。画面のどこを狙っているかを筐体側が
  常に正確に把握できる構造で、本企画とは前提が異なる（後述）。
- **Sinden Lightgun（現行の家庭用ライトガン再現ペリフェラル）**: Webカメラで画面の縁
  （白枠）を認識し、実銃型デバイスの向きから画面上の狙点を絶対座標で逆算する方式。
  現行で最も精度が高いDIY/市販ソリューションだが、**「デバイスのカメラが常に画面を
  向いている」ことが前提**——本企画の「スマホを銃のように構える」持ち方（カメラが
  画面を向かない）とは根本的に相容れない。
- **Wii リモコンのIRセンサーバー方式**: センサーバー（赤外線の基準点）を画面上/近傍に
  固定し、リモコン側のIRカメラでそれを捉えて絶対位置を算出する方式。原理はSindenと同じ
  「外部の絶対基準点＋カメラ」で、同じ理由で本企画の持ち方とは両立しない。
- **スマホの姿勢センサーのみで狙いを取るアプリ・ミニゲーム**: `DeviceOrientationEvent`
  （iOS/Android双方のモバイルブラウザで対応、iOSは`requestPermission()`による明示許可が
  必要）は相対的な姿勢変化しか取れず、外部の絶対基準を持たないため、使い続けると
  ジャイロドリフトで狙点が実際の向きからずれていく。ARベースの照準ゲーム等はカメラ映像
  そのものを狙いの基準にすることでこの問題を避けているが、これも「カメラが画面を向く」
  前提であり本企画には使えない。

**差別化・結論**: 本企画が置かれた制約（カメラが画面を向かない持ち方）の下では、
外部の絶対基準点を使う既存方式（Sinden、Wiiリモコン方式）はいずれも採用できない。
残る現実的な選択は「ジャイロによる相対追従＋定期的な手動リキャリブレーション」であり、
これは妥協ではなく**この持ち方を選んだ時点で唯一整合する方式**。リキャリブレーションを
「リロード」という本来のガンシューティングの操作に重ねることで、UI的な違和感ではなく
ゲームプレイの一部として狙い直しを組み込む。この「制約から逆算した設計」自体が、
既存のライトガン専用ハード前提のタイトルにはない差別化点になる。

## 3. なぜこの方式か（技術的根拠）

- ジャイロ/加速度センサーは相対値しか取れないため、使用時間が延びるほど実際の向きと
  画面上の狙点がずれていく（ドリフト）。
- 本企画はスマホのカメラが画面を向かない持ち方を選んでいるため、カメラによる絶対位置
  補正（Sinden方式・ARマーカー方式）は使えない。
- 消去法として残る現実解は「相対追従＋手動リキャリブレーション」。リロード（弾切れ時に
  画面中央へスマホを構え直す動作）にリキャリブレーションを紐づけることで、プレイヤーに
  「システムの都合による操作」ではなく「ゲーム内の自然な動作」として提示する。
- iOS Safariでは`DeviceOrientationEvent.requestPermission()`によるユーザー操作起点の
  明示許可が必須（**要検証** — 実機での動作未確認、→ 未決事項）。

## 4. マイルストーン

| # | マイルストーン | 目的 |
|---|---|---|
| 1 | スマホブラウザ→PC間でジャイロ値をWebSocketで飛ばし、PC側で3D空間内のカーソル/照準を
    動かせることを確認する | 「狙って動かす」感触が本当に成立するかを最速で検証する |
| 2 | リロード動作でのリキャリブレーションを実装し、ドリフトが実用上気にならない範囲に
    収まるか検証する | この企画の技術的な核心である不変条件2（`CLAUDE.md`）の成立可否を
    確定させる |
| 3 | 固定敵1体を撃つだけの最小シーンを作り、「撃つ」感触（着弾フィードバック・効果音・
    敵の反応）を詰める | 体験の核（§2）を実際に触って判断する |
| 4 | オンレールの敵配置・複数ウェーブを持つ短い1ステージを作る | ゲームとしての手触りを
    通しで確認する |
| 5 | 世界観・敵モチーフを確定し、正式なアセットに差し替える | 見た目を「仮」から本番へ |

## 5. 検討事項

- WebSocketの遅延がプレイフィールにどこまで影響するか（同一Wi-Fi内なら数十ms程度を
  想定しているが実測が必要）。
- 難易度調整の手段（敵の出現速度・体力・弾数制限等）。
- スマホ側の画面表示（狙点そのものを表示するか、リロードのタイミングだけ表示するか等）。

## 6. 対象外

- マルチプレイヤー（協力・対戦とも）。
- Switch等の専用ハードへの展開（当初の企画動機である配信ハードルの高さを理由に除外）。
- スマホ側のネイティブアプリ化・ストア審査を要する構成。
- カメラを画面に向ける持ち方を前提にしたトラッキング方式（Sinden方式・ARマーカー方式等）。

## 8. 将来の拡張

- **スコアリング（実装済み、2026-09-06）**: 敵を倒すごとに得点（`Target.PointValue`）が入り、
  ステージクリア時にシーン単位のローカルハイスコア（PlayerPrefs）と比較・更新する。
  タイムアタックや複数プレイヤー間のランキングは未決事項#5として残っている。
- **複数ステージ・ボス戦（実装済み、2026-09-06）**: `Milestone4_Stage`に加えて
  `Stage2_BossRush`（4ウェーブ、3発当てるまで倒れないパンプキンボス）を追加。
  `TargetHitState`の`hitPoints`で「倒れるまでの被弾数」を敵ごとに設定できる
  （通常の野菜ゾンビは1発、ボスは3発）。ステージ間の自動遷移は未決事項#6として残っている。
- **難易度モード（実装済み、2026-09-06）**: アーケード（残機制）／カジュアル（無制限）を
  スマホ側で選択できる。このゲームにはまだ敵からの被弾という概念が無いため、フェールの
  条件は「狙って撃ってはずした」ことにした（`GyroReticleController.OnShotResolved`）。
  実機での遊び心地はまだ判断していない — 「はずれ＝残機減少」という設計そのものが
  この企画に合っているかは、実際に遊んでから見直す余地がある。
